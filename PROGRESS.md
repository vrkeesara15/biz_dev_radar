Plan ids are config maps (`STRIPE_PRICE_IDS` / `RAZORPAY_PLAN_IDS`, {plan: provider id}) so no price lives in code; a plan with no configured id makes checkout 502 rather than guessing. Both providers are called over raw REST with httpx (no SDK) so tests can mock every request with respx and no vendor client ends up in the dependency tree; the cost is that we own the request shapes (Stripe form-encoded, Razorpay JSON) and must follow their API versions by hand. `POST /billing/checkout` never changes the plan; only a verified webhook does, so a user who abandons the hosted page keeps the old plan.
- OQ-57 (§10.3 / M7-04 webhook trust and idempotency) Webhooks are the only unauthenticated mutating routes (PUBLIC_ROUTES in tests/isolation/factories.py): authentication is the provider HMAC over the RAW body (Stripe `t=<ts>,v1=<hex>` over "<ts>.<payload>" with a 300 s replay window; Razorpay hex HMAC of the body) and nothing is read from the payload before it verifies — a bad, missing, stale or tampered signature is 400 with no row written. Idempotency is a unique (provider, event_id); Razorpay does not put an id in the body, so `X-Razorpay-Event-Id` is used and, when absent, "<event>:<entity id>" — a provider that redelivers with a fresh header id would double-count, which is why plan changes are idempotent by value (set tenants.plan, no deltas). The tenant is resolved from metadata/notes first (Stripe `metadata.tenant_id` + `client_reference_id`, Razorpay `notes.tenant_id`) and only then from billing_customers on the owner role; an event that resolves to no tenant is answered 200 "ignored" so the provider stops retrying something we can never attribute.
- OQ-58 (§11 / M7-04 audit of webhooks) A webhook has no user, so the audit middleware (which needs `request.state.user` for a tenant) writes nothing for it. `BillingService.apply_event` therefore writes its own audit_log row (action `billing.webhook`, user_id NULL, object tenant, meta provider/kind/event_id/plan_before/plan_after) inside the same transaction as the plan change, and `test_every_mutating_route_under_api_v1_is_audited` now exempts exactly the two webhook routes with the exempt set asserted so no other route can slip out. An unsigned webhook (400) leaves no audit row at all: there is no verified tenant to write it into, and audit_log.tenant_id is NOT NULL.
- OQ-59 (§10.1 / M7-04 GST invoices) Invoices are issued by Razorpay; we record the GST split, we do not generate the PDF. `core.billing.gst_breakdown` treats the charged amount as GST-INCLUSIVE, rounds the taxable value and derives tax as (total - taxable) so the lines always add up to what was charged; intra-state (place of supply == the first two digits of BILLING_GSTIN) splits CGST/SGST, otherwise IGST. Defaults: SAC 998314, 18% (`BILLING_GST_RATE_PCT`). Place of supply comes from the customer's `notes.place_of_supply`, else the state code of their GSTIN — a customer with neither is billed as inter-state (IGST), which is the safe default but should be confirmed with a CA before the first Indian invoice, together with reverse charge for unregistered recipients and the export-of-services case (§14 counsel item).

- OQ-60 (§11 / M7-07 consent at signup) There is no auth/signup route on main yet (`/api/v1/auth/*` is reserved in PUBLIC_ROUTES but unimplemented), so "consent notice recorded at signup" is served by `POST /api/v1/me/consents` {kind, version}: the signup wizard calls it right after the first `/me` provisioning call, and Settings > Privacy calls it again when a version is bumped. The route is open to EVERY tenant role (a viewer must be able to consent for themselves) and is idempotent per (tenant, user, kind, version) — re-accepting returns the original row with created=false, while bumping `DPDP_NOTICE_VERSION` / `PRIVACY_POLICY_VERSION` / `TERMS_VERSION` writes a new row and never touches the old one. Nothing yet BLOCKS an un-consented user from using the API; enforcing that belongs with the auth task that owns signup.
- OQ-61 (§11 / M7-07 what an erasure removes) `delete_tenant` derives the table list from SQLAlchemy metadata (every table with a tenant_id column) and deletes children-first in reverse `sorted_tables` order, so a table added later is erased the day it exists; the integration test re-derives the same list from information_schema, which would also catch a table the ORM does not know about. audit_log is the single retained table (SPEC 11: the trail must outlive the data) and the `tenants` row is kept and stamped `deleted_at` so the id can never be reused; `POST /tenant/{export,delete}` answer 409 afterwards. Global tables are deliberately untouched: `opportunities` and friends are public notices owned by nobody. `users` rows are global too, so an erasure deletes only those left with no membership anywhere — a user who also belongs to another tenant keeps their account. The data_requests row that asked for the deletion is itself deleted (it is tenant-scoped), so the outcome lives in the retained `privacy.tenant_delete` audit row, written before the deletes so it shares their transaction.
- OQ-62 (§11 / M7-07 export shape and delivery) A tenant export is one zip written to the tenant's own residency bucket at `tenants/{tenant_id}/exports/{request_id}.zip`: `manifest.json` (row counts, file count, region, generated_at, files_missing_from_storage), `tables/<name>.json` per tenant-scoped table and `files/<file id>-<name>` for every uploaded object. It is registered as a normal `files` row so the owner downloads it through the existing signed-URL route, and the request also carries a ready signed URL in `details.url`. Two consequences to revisit at scale: the whole export is built in memory (fine for an MVP tenant, not for a tenant with gigabytes of documents — stream to storage when that happens) and the export zip is itself a tenant file, so it is included in the NEXT export and removed by an erasure. No retention/expiry job deletes old exports yet.
- OQ-63 (§11 / M7-07 who answers a correction or erasure of one principal) `access` is answered inline (the response carries the caller's own rows from memberships, consents, data_requests, user_notification_prefs, files they uploaded and their audit_log entries) because we can compute it exactly. `correction` and `erasure` for a SINGLE data principal inside a live tenant stay `received` on the SLA clock for a human: deleting one member's rows from a shared tenant (their drafts, their uploads, their audit trail) is a judgement call the spec does not settle, and the tenant's own retention obligations may conflict. `sla_due_at` is created_at + `DATA_REQUEST_SLA_DAYS` (30) and `overdue` is computed on read, but nothing alerts on it yet — wire the SLA breach into the ops channel with the notification work.

- OQ-64 (§10.1 / M7-05 how traces reach Cloud Trace) The application speaks plain OTLP/HTTP to `OTEL_EXPORTER_OTLP_ENDPOINT` (`<endpoint>/v1/traces`) and knows nothing about GCP: the Cloud Trace credentials belong to an OpenTelemetry Collector sidecar on the Cloud Run service, so the same image runs unchanged in the US and Indian deployments and in local dev against `otel/opentelemetry-collector`. No endpoint means no TracerProvider is installed at all (the global stays the API's no-op default) and no exporter thread starts; `google-cloud-trace` is deliberately NOT a dependency. Instrumented: FastAPI (excluding /healthz), SQLAlchemy, httpx (so every adapter fetch is a child span) and — worker only — Celery. Adapter runs are therefore traced as the Celery task span plus its httpx children rather than a hand-rolled span per adapter; add an explicit span in `services.source_runner` if per-source timing needs to be a first-class attribute rather than a task attribute.
- OQ-65 (§11 / M7-05 what Sentry is allowed to see) `send_default_pii=False`, `max_request_body_size="never"` and a `before_send` that (a) redacts any field named like a secret or a regulated identifier at any depth (authorization, cookie, stripe-signature, x-razorpay-signature, api_key, token, password, ein, pan, gstin, tan, bank_account, ifsc, email) and (b) masks email / EIN / PAN / GSTIN / "Bearer <token>" shapes INSIDE free text, because the leak we actually fear is a solicitation excerpt or a stack-frame local, not a tidy field. The value patterns are deliberately conservative (an over-eager regex makes crash reports useless), so an identifier in an unusual format can still slip through — the real defence is that bodies are never sent. The event is tagged tenant_id / request_id and the user is attached as an ID ONLY, never an email. `SENTRY_TRACES_SAMPLE_RATE` defaults to 0.0: OTel owns tracing, Sentry owns errors.
- OQ-66 (§10.1 / M7-05 request context in logs) `app/core/context.py` gained tenant_id/user_id contextvars next to the request id; `get_current_user` binds them the moment the bearer token verifies and `RequestIdMiddleware` clears both in its finally block, so `app/logging.py` can stamp request_id/tenant_id/user_id on EVERY structlog line without any call site passing them. Consequences worth knowing: a line emitted before authentication (public route, 401, middleware) carries only request_id — by design, and asserted; and a Celery task has no request, so its lines carry none of the three and the job entrypoints log tenant_id/source_id/request_id explicitly instead. JSON rendering is still tied to `APP_ENV=production`; there is no separate LOG_JSON switch.
- OQ-67 (§8 / M7-05 Langfuse tags) The Tracer protocol gained `run_started(run_id, kind, tenant_id, pursuit_id)`, called once by `AgentRunner.run`, so the Langfuse trace is created with tags `tenant:<uuid>`, `kind:<run kind>` and (when set) `pursuit:<uuid>` instead of being an untagged bag of generations. Per-step cost still goes to Langfuse as generation usage {input, output, total_cost}. Note that tagging with the raw tenant UUID sends a tenant identifier to Langfuse (EU) — acceptable because it is an opaque id and Langfuse is already a listed sub-processor for prompts and completions, but it is the reason the LLM trace destination must stay on the sub-processor list. Langfuse remains best-effort: the authoritative cost numbers are agent_steps.cost_usd and the usage_ledger llm_* metrics (OQ-46).
- OQ-68 (§11 / M7-01 ClamAV in the image) Virus definitions are NOT baked into the backend image: `freshclam` is ~300 MB and stale the day the image is built, so `backend/docker/clamd-start.sh` fetches them into /var/lib/clamav on first container start and then execs clamd. Consequences: the first minute of a cold container cannot scan, and `app/services/scanner.ClamAVScanner` already fails CLOSED (503, ScannerUnavailableError) while clamd is unreachable — which is the behaviour we want, but it means a cold-started api revision briefly rejects uploads. clamd is started only when SCANNER_BACKEND=clamav, so local/test containers never pay for it. If the cold-start window becomes a problem the fix is a sidecar with a persistent volume (or Cloud Run's mountable GCS bucket for the CVD files), not baking the DB into the image.
- OQ-69 (§10.1 / M7-01 Celery on Cloud Run) A Cloud Run *service* revision is only marked ready when the container answers on $PORT, but a Celery worker and beat speak only to Redis. `app/jobs/health_server.py` therefore starts a stdlib one-route HTTP server (`/healthz`, same JSON shape as the API plus a `component` field) next to Celery in the worker and beat containers, and the manifests set `run.googleapis.com/cpu-throttling: "false"` (a throttled worker stalls between requests) with minScale 1. Beat is pinned min=max=1 because two beats double every periodic task. The health route is deliberately shallow: it reports the process, not Postgres, so a wedged broker does not cause Cloud Run to recycle a container that is merely idle. If Cloud Run worker pools (no HTTP contract) become GA in these regions, worker/beat should move to them and this shim can go.
- OQ-70 (§10.1/§12 / M7-01 who owns the Cloud Run objects) `infra/cloudrun/**` is GENERATED by `python -m app.jobs.generate_cloudrun` from the adapter registry and committed so the Cloud Run surface shows up in review; `tests/unit/test_cloudrun_manifests.py` regenerates it and fails on drift, so a new adapter cannot land without its job. But Terraform (M7-02) is the authoritative deployer — the YAML is a readable spec plus an escape hatch for `gcloud run services replace` via `infra/cloudrun/render.sh`, and every environment-specific value is a `${PLACEHOLDER}` listed in `generate_cloudrun.PLACEHOLDERS`. Two consequences: the same facts (image, service account, connector) are expressed twice, so the two must be kept honest by review; and disabled adapters (`enabled = False`) get no job and no Scheduler trigger, which is asserted. Image sizes on this machine: backend 897 MB (Tesseract eng+hin + ClamAV dominate), frontend 321 MB; a clean backend build takes about 3 minutes.

- OQ-71 (§3/§11 / M7-08 what a support-access grant is) SPEC 3 says a platform admin has no tenant-data access "unless support access is granted and logged". The logged half already existed (audit_log via `support_access_session`); M7-08 adds the granted half as `support_access_grants`, a GLOBAL table (no tenant_id — it carries `target_tenant_id`, no RLS policy, no app-role DML grant at all, listed in RLS_EXEMPT_TABLES with that reasoning) written and read only through the owner-role admin session. A grant belongs to ONE admin and ONE tenant, is time-boxed (5..480 minutes, default 60, clamped in `core.admin.clamp_support_minutes`) and expires by itself; another admin's grant does not help. `require_support_access(tenant_id)` gates the only admin route that reads tenant-scoped rows today, GET /admin/tenants/{id}/audit-log, and answers 403 with an explanation otherwise. Two gaps on purpose: there is no revoke ENDPOINT yet (the `revoked_at` column exists and is honoured, so revoking is an owner-role UPDATE until the console needs a button), and no other admin route reads tenant content, so the dependency currently guards one route — every future one (drafts, exports during support) must take it too.
- OQ-72 (§10.3 / M7-08 admin route shapes and double auditing) GET /api/v1/admin/tenants changed from a bare list to a page object {items,total,page,page_size,pages} because the console needs q + pagination; the one test that read the list shape was updated. Mutating admin routes must NOT use `AdminSessionDep`: that dependency writes an `admin_access` audit row per use, and the audit middleware already writes exactly one row per mutation (asserted by test_every_mutating_route_under_api_v1_is_audited), so PATCH /admin/tenants/{id} takes a new `AdminWriteSessionDep` (owner session, no audit row of its own). A plan/is_internal change additionally writes ONE `admin.tenant.update` row into the TARGET tenant's trail — but only when a value actually changes, so an empty PATCH stays a single-row no-op and the tenant's own audit log is not polluted by admin reads that changed nothing. Same split as support access: the middleware row lands in the admin's (internal) tenant, the service row in the tenant being administered.
- OQ-73 (§10.4 screen 9 / M7-08 usage, cost and health) Usage is reported per tenant per 'YYYY-MM' from usage_ledger (llm_tokens_in/out, llm_cost_microusd, OQ-46) plus a count of agent_runs whose created_at falls in the month; `notifications` is in the response as an explicit null because SPEC 10.4 asks for it and the notifications table only arrives with M4 — fill it there rather than adding a second usage route. Cost crosses the wire as BOTH `cost_microusd` (integer, authoritative) and `cost_usd` (float, convenience); the frontend formats from the integer. GET /admin/health is deliberately cheap and synchronous: a `SELECT 1`, a kombu `ensure_connection` ping at CELERY_BROKER_CONNECT_TIMEOUT (a blocking call inside the event loop — acceptable for an admin-only route with a 2 s default, but it must not be added to /healthz), and a CONFIG-level storage check (backend + bucket names, `degraded` for the local filesystem backend) with no round trip to S3/GCS, so a slow bucket cannot hang the console. Adapter health is rolled up worst-first (failing > degraded > not_implemented > unknown > ok).
- OQ-74 (§11/§12 / M7-02 a deployment serves ONE residency) `app/services/storage.bucket_for_region` picks the bucket from the TENANT's `data_residency`, not from the deployment's REGION, so a `prod-us` deployment that somehow acquired an Indian tenant would need a GCS_BUCKET_IN. Rather than give it one, each environment sets the foreign region's bucket name to `<prefix>-no-foreign-residency`, a bucket that does not exist: the write fails loudly instead of silently landing Indian documents in Virginia. Consequence: nothing in the code prevents CREATING a foreign-residency tenant in the wrong deployment — it just cannot store files, so the failure surfaces as a 500 on the first upload. Signup should refuse the mismatch outright (the auth task owns signup, OQ-60). `terraform output residency_ok` is the standing check that bucket, CMEK key, DB, backups, Redis and the Secret Manager replicas are all in the environment's own region.
- OQ-75 (§11 / M7-02 who puts the secret values in) Terraform creates one EMPTY Secret Manager secret per `SECRET_SETTINGS` name and grants the three runtime service accounts `secretAccessor`; it writes a version for exactly three — DATABASE_URL, DATABASE_URL_OWNER and REDIS_URL — because it generated those passwords itself (`random_password`, so they DO land in Terraform state, which is why the state bucket is per-environment, in-region, and must be access-restricted like any other store). Every other value (ANTHROPIC_API_KEY, SAM_API_KEY, Stripe, Razorpay, AUTH_SECRET, FIELD_ENCRYPTION_KEY, Sentry, Langfuse) is added by a human with `gcloud secrets versions add`. A Cloud Run revision therefore FAILS TO START until they exist — the right failure, but it means a fresh environment needs the secret-filling step in its runbook before the first deploy, and rotation is manual: a new version is picked up on the next revision, not live.
- OQ-76 (§13.1 / M7-02 Terraform state and preview revisions) The GCS backend is a PARTIAL configuration (`backend "gcs" {}` plus a committed `backend.hcl`) because a backend block cannot read variables; the `state_bucket` variable exists only so the intended bucket is in code and in an output, and a test asserts the two agree. Two further choices: `google_cloud_run_v2_service` sets `ignore_changes = [client, client_version, template[0].revision]` so the per-PR preview revisions M7-03 adds out of band survive the next apply — the cost is that a revision changed by hand is invisible to Terraform; and `google_kms_crypto_key` carries `prevent_destroy`, so tearing down even a dev environment needs a deliberate state removal, which is the trade we want when the alternative is permanently unreadable objects. `terraform apply` was NOT run (no GCP project exists yet): `fmt -check -recursive` and `validate` on all four envs passed locally against google provider 6.50.0, and both are now a CI job.
- OQ-77 (§12 / M7-03 what "same image" is enforced by) A tag promotion never rebuilds: `resolve` looks up the digest of `<repo>/backend:sha-<commit>` with `gcloud artifacts docker images describe` and every downstream job passes `…@sha256:…`, while the composite action REFUSES an image reference without `@sha256:` before it touches anything. So prod-us and prod-in run bytes identical to what staging-in ran. Two consequences: tagging a commit that main never built fails `resolve` with an explicit message rather than building something new; and the front-end image bakes `NEXT_PUBLIC_API_BASE_URL` at BUILD time, so the one image that reaches all four environments carries the DEV api URL in its bundle. That is wrong for production and is the one place the "same image" rule leaks — the frontend must either read its API base at runtime (move it out of NEXT_PUBLIC_) or be built per environment. Recorded rather than fixed here because it belongs with the frontend config task.
- OQ-78 (§12/§13.1 / M7-03 what a preview environment is, and is not) A preview is a TAGGED, ZERO-TRAFFIC revision of the dev api and web services (`gcloud run deploy --tag pr-<n> --no-traffic`), reachable at `https://pr-<n>---bidradar-dev-api-<hash>.a.run.app`, torn down by `--remove-tags pr-<n>` when the PR closes. It deliberately SHARES the dev database and runs NO migration: a per-PR Cloud SQL instance costs more than the review it enables, and the deploy pipeline already requires migrations to be backward compatible (schema first, traffic second). The consequence is real and worth knowing: a PR whose migration is not backward compatible will show a broken preview, because the new code is running against the old dev schema — that is information, not a bug in the preview. Previews are also skipped for forks, because a fork cannot mint an OIDC token for our project and giving it one would hand a stranger the deploy identity.
- OQ-79 (§13.1 / M7-03 approvals, rollback and what the pipeline will not do) staging-in, prod-us and prod-in are separate GitHub Environments, so "required reviewers" is configured in repository settings, not in YAML — the workflow only names the environment, and prod-us/prod-in are a matrix with `max-parallel: 1` so each gets its own approval and India does not go out while the US deploy is still failing. Rollback is a traffic shift (`update-traffic --to-revisions`), which does NOT roll back the database; a bad migration is recovered with PITR (docs/runbooks/restore-drill.md), and the runbook says so. The pipeline deliberately does NOT run `terraform apply`: a plan that can destroy a Cloud SQL instance is applied by a person after review. `workflow_dispatch` was also removed — a deploy is caused by a merge or a tag, and anything else is the by-hand gcloud sequence in the runbook.
