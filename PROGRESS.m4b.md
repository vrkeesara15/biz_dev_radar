## Open questions

- OQ-90 (§6 keyword signal with no keywords) A profile with no include keywords has nothing to match on, so `keyword_match` is UNKNOWN (0.5, note "no include keywords") rather than 0. OQ-73 scores a profile that lacks data 0 for `code_match` because codes are the primary expression of what a company sells; keywords are optional enrichment on top of them, and zeroing a 10-weight signal would punish every profile that finished the wizard without typing keywords. Same for keywords that all carry weight 0.
- OQ-91 (§6 "keyword BM25 ... normalized 0-1") Postgres has no BM25; SPEC 6's acceptance line names `ts_rank_cd`, whose raw cover-density rank is unbounded (it grows with the number of occurrences). Each per-term rank is therefore normalised with Postgres's own flag 32 (`rank / (rank + 1)`) rather than by dividing by the rank of the profile's own keyword string against itself: flag 32 needs no reference document, is scale-free, and is stable when the owner edits their keyword list. One tsvector is built per notice from title (weight A), summary_ai + description (B) and the parsed document chunks (C, capped at 120k characters so the 1 MB tsvector limit can never be hit), so the calibration reads: one occurrence in the title = 0.50, one in the description = 0.29, one inside a document = 0.17, a term repeated throughout the notice -> 1. The profile's own `profile_keywords.weight` values are the COMBINATION weights (weighted average across terms), not tsquery weights, because a tsquery weight label selects document weights rather than scaling a term.
- OQ-92 (§6 stage 3 "rationale=null with flag") `matches` has no boolean column for the flag and adding one for a transient state is not worth a schema change, so the outcome lives in `matches.breakdown["rationale_status"]`: `ok` (the model answered), `cached` (reused from the same (opportunity_version, profile_version) row), `below_threshold` (score < 50, never called), `failed` (the model never produced valid JSON within LLM_OUTPUT_RETRIES; `breakdown["rationale_error"]` carries a 300-char reason) and `unavailable` (no ANTHROPIC_API_KEY). `rationale` itself stays NULL for everything but ok/cached, so the frontend can render on `rationale` alone and use the status only to explain WHY it is missing. The failed attempt is still metered: AgentRunner writes the agent_steps row and the usage_ledger llm_* rows under the match's tenant even when the step failed.
