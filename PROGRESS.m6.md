Format per entry: task id · what changed · how verified.

## Open questions

- OQ-110 (§9 / M6-01 who may do what on the board) SPEC 3 gives bid managers "move pursuits"; the finer split is a decision. Pursue and Pass are bid-manager (they start paid agent work / close a card), Watch is writer-and-up (it costs nothing), PATCH is writer-and-up for a FORWARD move but bid-manager for an assignment, a BACKWARDS drag and reopening a terminal pursuit (`app.core.pursuit_stages`: a writer must not undo Gate 1 by dragging a card). Every tenant role reads GET /pursuits.
- OQ-111 (§9 / M6-01 which profile a board action uses) `POST /opportunities/{id}/pursue|watch|pass` take an OPTIONAL `profile_id`. With exactly one active profile the server picks it; with several it answers 409 {error: profile_required, profile_ids[]} rather than guessing, and the UI asks. A tenant with no active profile gets 404.
- OQ-112 (§9 / M6-01 pursue never runs the pipeline inline) Pursue creates the `pipeline` agent run and hands it to Celery; it never falls back to running in the API process the way POST /pursuits/{id}/agents/run does, because a board click must not block on a 30-minute pipeline. Under CELERY_TASK_ALWAYS_EAGER (tests) and when no broker answers, the run row is left `queued` and the response says so in `agents.reason`. A plan whose `agent_budget_usd_month` is 0 (free) opens the card and enqueues nothing.
- OQ-113 (§9 / M6-01 stage vocabulary storage) `pursuits.stage` stays `varchar(32)` with a CHECK listing the eleven SPEC 9 stages (constraint `ck_pursuits_stage`) rather than becoming a Postgres enum: a new stage is then one migration instead of an enum rewrite, and `app.core.pursuit_stages.STAGES` stays the single source of truth for the model, the migration and the API validator. `POST /pursuits/{id}/decision` (Gate 1) is deliberately NOT defined here — it belongs to the parallel bid/no-bid branch; M6 only reads `pursuits.decision`.
- OQ-114 (§9 / M6-02 the Indian EMD offset) SPEC 9's acceptance line reads "IN pursuits add emd_bg_ready and dsc_check (due-3d)", which can be read as both at due-3d. Implemented as emd_bg_ready = due-5d and dsc_check = due-3d: a bank guarantee takes days to raise, a DSC check is a same-week task, and pairing EMD with the internal draft date is what an Indian bid desk actually plans against. One constant in `core.key_dates.DEADLINE_OFFSET_HOURS` if the owner wants both at 3 days.
- OQ-115 (§9 / M6-02 what `now` does in auto_dates) `auto_dates(notice, region, now)` never uses `now` to decide WHICH dates exist — a milestone whose moment has already passed is still created, flagged `is_past`, so the reminder ladder can report it overdue and an amendment that pushes the deadline out makes the same row future again. A notice with no `response_due_at` (forecast, sources sought) gets no derived dates at all.
- OQ-116 (§9 / M6-02 what an amendment does to an acknowledgement) When the buyer moves the deadline, every `source = 'auto'` row shifts, `pursuits.internal_due_at` follows, and any acknowledgement on a SHIFTED row is cleared with the note "the buyer moved the deadline; re-acknowledge this date" — "I have seen this" was about the old date. A row a human created or edited becomes `source = 'user'` and is never moved or cleared again, and an auto kind the notice no longer states (a withdrawn Q&A date) is deleted unless it had been edited.
- OQ-117 (§10.2 / M6-07 table names to reconcile at merge) SPEC 10.2 names the tables `tasks` and `comments`. This branch creates them as `pursuit_tasks` and `pursuit_comments` (models in app/models/collab.py, migration 0011) because the parallel M5 branch is adding its own `tasks` table for the drafters in migration 0007. The orchestrator must pick ONE pair of names at merge; everything here goes through `app.services.collab`, so the rename is that module, `app/models/collab.py`, the migration and the route bodies. The drafters should call the merged `create_task_from_placeholder` rather than writing rows themselves.
- OQ-118 (§3 / M6-07 who may close a task and edit a comment) Creating, reassigning, re-dating and deleting a task is writer-and-up. Closing (and re-opening) a task is open to EVERY tenant role, but only for a task assigned to that user and only when the request changes nothing but `status` — so a reviewer can tick off their own review without being able to rename or reassign work. Commenting and resolving follow SPEC 3's reviewer row (owner / bid manager / writer / reviewer); a viewer reads. Editing or deleting a comment is the author or a bid manager.
- OQ-119 (§8 / M6-07 [NEEDS INPUT] identity) A task made from a placeholder is keyed by (pursuit, agent, case-folded placeholder) in `pursuit_tasks.ref`, so re-running an agent never asks the same question twice and a task somebody already completed stays completed. Two DIFFERENT agents asking for the same fact each get their own task, because each needs it in its own artefact. `[NEEDS INPUT]` with no label becomes "unspecified input", and a placeholder is never allowed to span a line so a stray bracket cannot swallow a paragraph.
- OQ-120 (§10.3 / M6-04 how the iCal link authenticates) A calendar client cannot hold a session, so GET /api/v1/calendar.ics is a PUBLIC route whose `token` query parameter is the credential: an HS256 JWT (AUTH_SECRET, no expiry — a feed URL that dies in two weeks is worse than useless) naming the tenant, the user and a `nonce` that must still equal `user_notification_prefs.calendar_token`. POST /api/v1/me/calendar-token issues or rotates the nonce, which revokes every link handed out before. Nothing is read from the token before the signature verifies, and a bad / foreign / rotated one is 401.
- OQ-121 (§9 / M6-04 whose dates are in the feed) The feed carries the key dates of pursuits the reader OWNS plus those they have a task on (`pursuit_tasks.assignee_user_id`), which is the closest thing the data model has to SPEC 9's "assignees". Times are absolute UTC DTSTART/DTEND with a 30-minute block; the dual time-zone string and the deep link live in the DESCRIPTION, so a client showing its own zone still displays the buyer's clock.
- OQ-122 (§7 / M6-04 where a calendar credential lives) A Google/Outlook connection is PER USER, so it is a `calendar_connections` row (tenant_id + user_id + provider) rather than an `integrations` row (per tenant, M4-11); the OAuth token is a `secret_ref` resolved through app.services.secrets, never a column. There is no OAuth CONSENT flow yet: rows are created out of band (or by the settings UI once the flow exists) and the API only lists and disconnects them. `pursuit_dates.sequence` is an explicit counter bumped on every change, because RFC 5545 requires a strictly higher SEQUENCE for a calendar to accept an updated event and a timestamp-derived number is too coarse for two edits in the same minute.
- OQ-123 (§9 / M6-04 a push failure never blocks the date) Provider pushes are best effort: a `CalendarPushError` is recorded on `calendar_connections.last_error` and `calendar_events.last_error`, logged, and swallowed. The iCal feed is always correct even when a push is not, and a recalculation triggered by an amendment can never be aborted by a calendar outage. A provider event whose key date was deleted while the provider was down is therefore orphaned; a reconciliation sweep is a follow-up.
- OQ-124 (§7 / M6-05 the three WhatsApp gates) WhatsApp Business forbids business-initiated free text, so `WhatsAppChannel` never composes a message: it picks a PRE-APPROVED template name from settings (WHATSAPP_TEMPLATE_DEADLINE / WHATSAPP_TEMPLATE_HIGH_MATCH) and fills four numbered variables (title, buyer, when-or-score, link), each collapsed to one line and clipped to 200 characters. It sends only when (1) the event is `deadline_reminder` or `high_fit_match` — SPEC 7's only two WhatsApp rows, (2) the tenant's region is `in`, and (3) the user has `phone_e164` + `phone_verified_at`. Any gate that fails is a SKIPPED delivery (no retry, no email fallback), and no network call is made. There is no phone-VERIFICATION flow yet: `phone_verified_at` is set out of band until the settings UI owns it.
- OQ-125 (§7 / M6-05 receipt authentication) POST /api/v1/webhooks/whatsapp/{provider} is public like the billing webhooks. Gupshup signs the raw body with HMAC-SHA256, which `WHATSAPP_WEBHOOK_SECRET` verifies; Twilio's real scheme signs the request URL plus the sorted POST parameters, which needs the public URL the request arrived on, so for now a Twilio receipt is verified against the same shared secret in `X-Twilio-Signature`. With no secret configured, receipts are accepted unsigned — acceptable because a receipt can only ever move a `notification_deliveries` row we created, addressed by its `provider_ref`, and never backwards (a late `delivered` cannot demote an `opened`). The route is added to the audit middleware's asserted exempt set for the same reason the billing webhooks are (no user, no tenant).
- OQ-126 (M6-05 the one derived infra/ change) `app/core/config.SECRET_SETTINGS` gained gupshup_api_key, twilio_auth_token and whatsapp_webhook_secret, and `tests/unit/test_cloudrun_manifests.py` regenerates `infra/cloudrun/**` and fails on drift. The 14 generated manifests were therefore re-rendered with `python -m app.jobs.generate_cloudrun` and committed — the only infra/ change in this branch and a purely additive, derived one (three more `${SECRET_PREFIX}-*` secretKeyRefs per service/job), exactly as the M4 worktree did for its three new credentials.
- OQ-127 (§9 / M6-03 "in the user's time zone") A deadline is ONE instant, so the ladder is computed on absolute UTC moments and a US reader and an Indian reader of the same key date are reminded at the same second — each simply sees their own clock, rendered by `core.display_time` (the payload carries the buyer's `due_display`, and every Recipient carries their own tz). Reading "times computed in the user's tz" as per-user firing times would mean sending the same 24-hour reminder twice for one deadline. What IS per user is quiet hours: each recipient's delivery instant goes through `notify.scheduling.deliver_at`, whose 72-hour urgency override means the late rungs are never deferred.
- OQ-128 (§9 / M6-03 idempotency and the overdue cap) A rung's `sent_at` is stamped in the SAME transaction as its dispatch, so two overlapping five-minute ticks cannot send it twice (the Dispatcher's idempotency key, `<date>:<label>:<epoch>`, is a second belt). Rungs already in the past when a date is created are never generated, so a notice opened two days before its deadline gets no "7 days to go". Overdue rungs are added lazily, at most `MAX_OVERDUE_PER_PASS` (3) per tick, so an imported deadline from months ago produces a handful of reminders rather than hundreds. A rung that comes due once the pursuit has left the open stages records `skipped_reason` instead of sending.
- OQ-129 (§9 / M6-03 what escalation means) Level 0 reaches the pursuit owner, level 1 adds EVERY bid manager in the tenant, level 2 adds every tenant owner — the roles, not one named person, because the data model has no "the bid manager of this pursuit". Acknowledging the key date drops the rung back to level 0 at send time (the level is recomputed from the acknowledgement when the rung fires, not when it was created), so the owner still gets their reminder and nobody is escalated to.
- OQ-130 (§4.1 / M6-06 what an expired credential blocks) Only an expired SAM registration (US) or DSC (IN) sets `company_profiles.blocked_for_bids`; an expired GeM id, certification or insurance policy is a reminder, not a block, because the tender decides whether it matters (that is the eligibility engine's job, OQ-23). The block is recomputed from scratch on every daily run, so renewing a credential clears it the next day without a second endpoint. A blocked profile answers 409 {error: profile_blocked_for_bids, reason} on POST /opportunities/{id}/pursue but WATCHING is still allowed — watching starts no bid. There is no manual override route yet.
- OQ-131 (§7 / M6-06 one reminder per window) The 60/30/7 reminders are de-duplicated by the notification idempotency key (`expiry:<item id>:<window>`), not by a column on each credential table: a job that runs twice, or catches up after a missed day, sends nothing extra, and crossing into a tighter window is a different key so it sends again. `window_for` reports the TIGHTEST window that applies, so a job that skipped a week says "7 days", not "30". The stale-pursuit nudge is keyed `stale:<pursuit>:<date>` (once a day) and the matrix re-check by the opportunity version.
- OQ-132 (§9 / M6-06 what counts as "activity") `pursuits.activity_at` is bumped by `services.pursuits.touch` from every stage move, board action, key-date create/edit, task create/close and comment. Agent runs do NOT bump it yet — `AgentRunner` has no pursuit handle in its finish path; wire it there (or from the pipeline job) when the M5 branch lands, otherwise a pursuit worked on only by agents can look stale after five days.
- OQ-133 (§9 / M6-08 what "pipeline value" counts) `pipeline_value_by_stage` covers the OPEN stages only — a submitted, awarded, lost or cancelled pursuit is not pipeline. The figure per pursuit is the notice's `estimated_value_max_usd`, falling back to `estimated_value_min_usd`; a notice with neither contributes nothing rather than a guess. BOTH currencies are derived from that one USD figure (`core.dashboard.usd_to` divides by the same FX table `core.money.to_usd` multiplies by), so the USD and INR columns can never disagree — the INR column is therefore a converted total, not a sum of native INR values. A missing INR rate degrades to 0.00 rather than failing the home screen.
- OQ-134 (§9 / M6-08 hours saved and "packages submitted") Nothing measures hours saved, so `avg_hours_saved_per_package` is the `HOURS_SAVED_PER_PACKAGE` setting (default 20) and `hours_saved_total` is that times the packages submitted; the response carries `hours_saved_basis` saying so in words, so the number is never mistaken for a measurement. "Submitted" counts pursuits at `submitted`, `awarded` and `lost` — a package that went on to be won still went out of the door. Every rate (win rate, alert precision) is null, not 0, when its denominator is empty.
- OQ-135 (§9 / M6-08 alert precision before match_feedback exists) `match_feedback` belongs to the parallel matching branch and does not exist here. `services/dashboard.feedback_precision` checks `information_schema` first and answers (None, 0) when the table is absent, and catches a ProgrammingError when it is present with a different shape — so `alert_precision` is null today and lights up at merge without a code change, provided the table keeps a `verdict` column whose useful values are among ('useful', 'good', 'relevant'). Reconcile that column name with the matching branch at merge.
