## Open questions

- OQ-70 (§6 stage 1 "response date in the future") A notice whose status is `cancelled` or `awarded` is dropped by the same filter (reasons `status_cancelled` / `status_awarded`) even when its deadline is still ahead: scoring a cancelled tender would raise alerts for something nobody can bid on. Recompete watch (awards_enrichment.recompete_watch on the notice or its solicitation number) keeps past-due AND terminal notices, as the spec's parenthesis intends. A deadline that is unknown (None: forecasts, sources sought) is not "past" and is kept.
- OQ-71 (§6 set-aside cap) US set-aside codes are the SAM.gov codes stored by M2 (OQ-30): 8A/8AN -> 8a, HZC/HZS -> hubzone, WOSB(SS) -> wosb (edwosb also qualifies), EDWOSB(SS) -> edwosb, SDVOSB/SDVOSBC/SDVOSBS -> sdvosb, VSA/VSS/VOSB -> vosb (sdvosb also qualifies), SBA/SBP -> SBA small status for ANY of the notice's NAICS (core.eligibility). Programmes the profile cannot express (LAS local area, IEE/ISBEE Indian economic enterprise, BICiv) are recorded as "not evaluated" and never capped. An `unknown` size (no USD receipts / head count, no NAICS, no bundled standard) never caps either: the eligibility signal reports it as 0.5 rather than the hard filter penalising missing data. Indian reservations are still free text until the M3 adapters land, so `reservation` is classified by regex (MSE/MSME, SC/ST, women, startup, Class-I/Make in India) against Udyam category, mse_ownership, DPIIT number and local_supplier_class; when M3 normalises reservation codes, swap the regex table for a code map in one place (`core/matching/filters._IN_RULES`).
- OQ-72 (§6 blocked buyers) Blocked buyers match after core.normalize.buyer normalisation (case, punctuation, legal suffixes, leading "the") as an equal name OR a whole-word phrase inside any buyer level (org, sub-org, office, hierarchy), so blocking "Energy" blocks "Department of Energy" but not "Energetic Systems Agency". Substring matches inside words are deliberately not used.
- OQ-73 (§6 stage 2 code match / geography unknowns) SPEC 6 gives "missing data = 0.5" only for eligibility; the same rule is applied where the NOTICE lacks the data: a notice with no code in any scheme scores code_match 0.5 ("notice lists no codes", common on Indian portals), an unknown place of performance scores geography 0.5, an unknown buyer scores buyer affinity 0.5 and an unknown estimated value scores value fit 0.5. A PROFILE that lacks the data is the owner's gap and scores 0 (no codes) or 1 (no state/city targets = whole already-filtered country; no value range = 0.5 since "no preference"). Value fit uses the INR range against INR notices when the profile has one, else the USD copies (core.money FX). Per-signal weighted values are rounded to cents before summing, so the breakdown always adds up to the stored score.
- OQ-74 (§6 / §5.3 US eligibility keys) No US requirements extractor exists yet (M5), so the US path reads a tolerant key set from `opportunity.eligibility`: `requires_small_business` (bool; when absent it is DERIVED from a small-business or socio-economic set-aside code), `min_avg_receipts_usd` / `min_annual_revenue_usd` (number or "$5M"), `min_experience_years`, `required_certifications` (names normalised like core.eligibility_in: "ISO 9001" == iso_9001), `required_registrations` (sam -> company_profiles.sam_status/sam_expires_on, falling back to registrations rows; other kinds -> registrations rows). The M5 extractor should emit these keys (or `core/matching/eligibility_signal.CriteriaUS.from_dict` gains the aliases). The IN path takes `due_on` from `response_due_at` when the extracted criteria omit it, so a DSC that lapses before the bid due date fails as OQ-23 intends; EMD stays informational and is excluded from the average.
