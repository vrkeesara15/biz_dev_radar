## Open questions

- OQ-30 (§5.3 set_aside "enum") SAM.gov publishes ~20 set-aside codes (SBA, 8A, HZC, SDVOSBC, WOSB, EDWOSB, ...) and Indian portals use free-text reservations. `set_aside` and `reservation` are stored as short text codes (normalised in app/core/normalize) rather than a Postgres enum, so a new code never breaks ingestion. Matching (M3) should compare codes, not display names.
- OQ-31 (§5.1 / M2-01) Where does the `sources` row sync run? On API startup (lifespan, best-effort: a DB outage logs a warning and the API still boots) and inside `run_source`'s caller (M2-16 job entrypoint should call `sync_sources` first). The FixtureAdapter lives in tests (tests/adapters/fixture_adapter.py) and is registered only for the duration of a test via `registry.temporarily()`, so no `fixture` source row appears in real databases.
- OQ-32 (M2-03 vs M2-01 order) `sources`/`source_runs` are created by migration 0003 already in M2-01 (acceptance needs them); 0003 currently revises 0001_m0_foundation and is re-pointed to 0002_m1_profile by the orchestrator at merge.
- OQ-33 (§5.2 SAM pagination) The Get Opportunities docs call `offset` a "page index" but every working client (and the acceptance line "offset until totalRecords") treats it as a record offset (offset += limit). The adapter uses record offsets; if a live smoke shows page-index semantics, change one line in `_fetch_window` (offset += 1) and the cursor stays valid.
- OQ-34 (§5.3 source time zone) SAM.gov returns responseDeadLine with an explicit UTC offset but postedDate/archiveDate as bare dates; naive values are interpreted in America/New_York and `source_tz` is recorded as America/New_York for every SAM notice (the buyer office's actual zone is not published). The UI shows the buyer zone alongside the user's, so a West-coast office deadline displays in ET, as SAM itself does.
- OQ-35 (M2-04 fixture provenance) There is no SAM.gov API key on this machine, so tests/adapters/fixtures/sam_opps/page{1,2}.json are SYNTHESIZED from the official Get Opportunities v2 documentation (field names, shapes and the documented sample record); values are invented. Grants.gov and USAspending fixtures are real captures. Replace the SAM fixture with a live capture during the nightly smoke (M2-14).
- OQ-36 (§5.2 SAM description quota) Pulling the description link costs one API call per notice, which a 10/day non-federal key cannot afford for a 1,000-record page. `fetch()` therefore yields listing records only; `fetch_detail(external_id)` (search by noticeid + description link) and header probing in `fetch_documents` are meant to run for NEW or CHANGED notices from the ingest pipeline / a detail job (M2-09/M2-16 wiring), and can be disabled with `probe_document_headers = False`. With a system-account key the job can simply call fetch_detail for every record.
- OQ-37 (§5.2 Grants.gov incremental) search2 has no "posted since" parameter; the UI's `dateRange` buckets (3, 7, 14, 21, 28, 35, 42, 49, 56 days; values taken from the live response's dateRangeOptions) are sent instead, picking the smallest bucket covering `since`. Older watermarks list everything posted+forecasted (a few thousand rows, no key needed). If a live smoke shows search2 ignoring dateRange, the adapter still works, just less incrementally.
- OQ-38 (M2-06 fixture provenance) tests/adapters/fixtures/grants_gov/search2_page{1,2}.json and fetch_332894.json are REAL captures (token redacted, publisher id and contact name anonymised, long arrays trimmed, one duplicate forecast hit 999001 added to page 2 to exercise keep-latest). fetch_forecast_334905.json is SYNTHESIZED (the capture only had a synopsis): its `forecast` block mirrors the synopsis field set plus the documented est* dates; replace with a live capture when the nightly smoke runs.
- OQ-39 (§5.2 USAspending semantics) USAspending awards are not opportunities, but every registered adapter must satisfy `normalize() -> OpportunityIn` (M2-14 contract tests). The adapter therefore emits award notices (notice_type award, status awarded) while the weekly job `services/spend.run_spend_stats` consumes the `AwardRecord` carried in raw.meta and never writes those awards to `opportunities`. Awards are bucketed by the fiscal year of their START date (fallback end date) and the query window is the last 3 fiscal years by action date; the API caps a query at 50,000 results (page 500 x 100), so profiles with very broad NAICS lists should pass `naics_codes` to narrow the query. Recompete candidates land in awards_enrichment with opportunity_id NULL, match_method recompete_candidate, recompete_watch true; M2-08 links them to notices.
- OQ-40 (§2 row 2 SAM.gov contract awards) No SAM key and no public capture of the contract-awards search exist on this machine, and the successor of the retired ATOM feed is documented only at the data-element level. The adapter therefore takes the endpoint from `SAM_AWARDS_API_URL` (default https://api.sam.gov/contract-awards/v1/search), the NAICS list from `SAM_AWARDS_NAICS` (or the constructor, so M1 profile codes can feed it), sends api_key + naics + signedDateFrom/To (MM/dd/yyyy, <= 1 year) + limit/offset, and reads responses through `core.normalize.sam_awards.ALIASES` (PIID, modificationNumber, solicitationNumber, effectiveDate, ultimateCompletionDate, obligatedAmount, baseAndAllOptionsValue, numberOfOffersReceived, naicsCode, productOrServiceCode, agency/department/office names, vendor.legalBusinessName/ueiSAM) with several accepted spellings each. tests/adapters/fixtures/sam_awards/page1.json is SYNTHETIC. First live smoke: confirm the endpoint and add any renamed keys to ALIASES / RESULT_KEYS (data changes only).
- OQ-41 (§5.4 versions on creation) A brand-new opportunity is stored at version 1 WITHOUT an opportunity_versions row; the versions table holds changes only (so "ingest twice with a moved deadline" yields exactly one version row). `opportunity.created` is published for new records and `opportunity.amended` for changes; matching (M3) should subscribe to both. The bus is in-process (services/events.py) with a `publisher` hook where the Celery producer plugs in at M2-16.
- OQ-42 (§5.4 detail freshness) `fetch_detail` (SAM description, header probes) is not called by the ingest pipeline itself; the runner ingests what `fetch()` returns. Wiring a detail pass for created/amended records (subscribe to the two events, call fetch_detail + fetch_documents, re-ingest) belongs with the scheduler task M2-16 / document parsing M2-12 so it can respect the SAM daily quota.

- OQ-43 (§5.4 dedupe scope) Both dedupe paths (cross-source key and fuzzy title) only merge records from DIFFERENT sources: within one source a repeated solicitation number is an amendment and is linked via parent_opportunity_id (M2-09), and same-source near-identical titles are usually re-postings the source itself distinguishes by external_id. `duplicate_of` is set once and never flipped when the loser later becomes richer (stable ids for matches/pursuits); the survivor's `extra.also_from` keeps every merged source link and is excluded from content_hash/diffs (VOLATILE_EXTRA_KEYS) so re-ingest of the survivor neither drops it nor records a version. The fuzzy window uses `response_due_at BETWEEN due - 1d AND due + 1d` (index-friendly, identical to abs(epoch diff) <= 86400). Search (M2-15) hides rows with duplicate_of set.
