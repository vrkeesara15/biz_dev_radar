## Open questions

- OQ-60 (§2 row 7 / M3-02 CPPP secondary page) The design named `eprocure.gov.in/cppp/tendersbyorganisationnew` as the second captcha-free page, but the capture of that URL is the portal's 404 page ("Oops! Page not found"); only `latestactivetendersnew` (7-column table: Sl.No, e-Published, Closing, Opening, Title/Ref.No./Tender Id, Organisation Name, Corrigendum) was verified. The adapter therefore treats "Tenders by Organisation" as best-effort: `CPPP_BY_ORG_URL` (default `/cppp/tendersbyorganisation`, empty = off) is fetched once per run; a 7-column tender table is parsed directly, an organisation index (GePNIC shape: S.No / Organisation Name / Tender Count with a link per organisation) is followed for the first `CPPP_MAX_ORGS_PER_RUN` (25) organisations, and a 404 or unknown layout only turns the run DEGRADED while the primary page still flows. `byorg.html` and `org_listing.html` fixtures are SYNTHESIZED from the GePNIC organisation index and the real 7-column rows (with an "Organisation Chain" column); replace them with live captures at the first smoke from an Indian IP. The detail `tendersfullview/<token>` link is kept as `source_url` (token = 'A13h1'-separated base64 segments: internal id, hashes, unix expiry, reference, tender code; the internal id is the stable `external_id` and the expiry is stored in `extra.detail_link_expires_at`), every record is `detail_status = manual` with `extra.manual_detail_url = /cppp/tendersearch` (CAPTCHA), and `fetch_detail` makes no request at all.

- OQ-61 (§2 row 8 / M3-03 GeM shapes) bidplus.gem.gov.in refused connections from the build host (OQ-14), so the GeM adapter is fixture-driven end to end: `GEM_BIDS_URL` (default the JSON backend of the public All Bids page, `/all-bids-data`) is POSTed the form field `payload` = {"page", "param": {"searchBid", "searchType": "fullText"}, "filter": {"bidStatusType": "ongoing_bids", "byType": "all", "sort": "Bid-End-Date-Latest", ...}} and the answer is read as Solr-style `response.response.{numFound,start,docs[]}` with one-item list fields through `core.normalize.gem.ALIASES` (b_id, b_bid_number, b_category_name, b_total_quantity, ba_official_details_minName/deptName/orgName/officeName, final_start_date_sort / final_end_date_sort, b_bid_type, b_is_ra ...). The listing fixtures (all_bids_page1/2, malformed, layout_change) and the bid PDF (built with PyMuPDF by tests/adapters/fixtures/gem/make_fixtures.py in the layout of a real GeM bid document, with a prompt-injection decoy line in the ATC) are SYNTHESIZED; the first smoke from an Indian/cloud IP confirms the endpoint, a possible CSRF token requirement and the key names (data changes in ALIASES / the payload builder). The acceptance line "GeM seller registration link surfaced in source_url" is read as: `source_url` is the official per-bid page (`GEM_BID_PAGE_URL`, the showbidDocument link, so link-back stays a government page) and the registration link (`GEM_SELLER_REGISTRATION_URL`) travels in `extra.gem_seller_registration_url` for the UI; the exact registration URL is configuration.

- OQ-62 (§2 row 9 / M3-05 GePNIC states) The acceptance line names `gepnic_ts | gepnic_ka | gepnic_mh`, but the OQ-14 pre-flight contradicts all three: mahatenders.gov.in serves `robots.txt: Disallow: /` (never crawlable), eprocurement.telangana.gov.in is a *custom* platform (JS login front page, no captcha-free listing table) and not GePNIC at all, and no Karnataka GePNIC host answered from the build host. The generic class is therefore configured for the three portals whose robots.txt permits crawling and whose pages were captured — `gepnic_tn` (tntenders.gov.in), `gepnic_up` (etender.up.nic.in), `gepnic_central` (etenders.gov.in, path `/eprocure/app`) — while `gepnic_mh` (health `robots_disallowed`) and `gepnic_ts` (health `not_implemented`) stay in `gepnic_configs.yaml` with `enabled: false` so the source ids, attribution and admin health exist without a request ever being made; Karnataka is a one-row YAML addition once a host is confirmed. Second decision inside the same task: GePNIC's "Latest Active Tenders" page is CAPTCHA-gated (unlike CPPP's `latestactivetendersnew`), so it is documented in the config and **never fetched**; the two captcha-free pages are the front-page "Latest Tenders" marquee and "Tenders by Organisation" (index + the first `GEPNIC_MAX_ORGS_PER_RUN` organisation listings). The organisation index / listing fixtures are SYNTHESIZED from the GePNIC table structure (the mahatenders capture was read as a structure reference only and never fetched by the adapter); replace them at the first smoke from an Indian IP.
