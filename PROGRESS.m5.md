## Open questions

- OQ-80 (§8 / §9 pursuits before M6-01) The agent pipeline needs a pursuit row to hang requirements, artifacts and cost caps on, but pursuits/stages/actions are M6-01. Decision: migration 0007_m5_agents creates a MINIMAL `pursuits` table (profile_id, opportunity_id, stage text default 'identified', owner_user_id, decision, internal_due_at, created_by, cost_cap_usd, unique (profile_id, opportunity_id)) with `services/pursuits.get_or_create` and an idempotent `POST /api/v1/pursuits {profile_id, opportunity_id}` (201 created / 200 existing, owner + bid_manager) so the workspace can be exercised now; M6-01 adds the stage enum/rules, key dates and `POST /opportunities/{id}/pursue|watch|pass` on top (it should route pursue through get_or_create). agent_runs.pursuit_id now carries a real FK (SET NULL).
- OQ-81 (§8 cost guard units) plan_limits.limit_value is an integer, so the tenant monthly LLM budget is `agent_budget_usd_month` in WHOLE USD (free 0, pro 50, enterprise NULL = unlimited; internal tenants unlimited via PlanService). The per-pursuit cap is money: `tenants.pursuit_cost_cap_usd numeric(12,2)` default 15 and `pursuits.cost_cap_usd` (NULL = tenant default), raised by approve-budget; the raise is recorded in audit_log (action pursuit.budget_approved, meta additional/previous/new cap, reason, run id) rather than a separate approvals table. Projection is deliberately rough (chars/4 tokens x configured price + an output allowance) and only stops a step BEFORE it spends; the ledger stays authoritative. A step without an estimator (collector) is free, but a run is still stopped when the month is already over budget and the step projects > 0.
- OQ-82 (§10.1 running the pipeline) `POST .../approve-budget` (and the coming `POST .../agents/run`) queue Celery task `bidradar.run_agents(run_id, tenant_id)` and fall back to running the job in the API process when no broker answers or `inline: true` is sent; when CELERY_TASK_ALWAYS_EAGER is on they also run in-process directly, because an eager task would call asyncio.run inside the API's event loop. The API process resolves the LLM from `app.state.llm` (llm_from_settings; tests inject FakeLLM) and storage/scanner from app.state, so an in-process run shares the API's fakes.
