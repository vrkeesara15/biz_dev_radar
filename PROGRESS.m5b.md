## Open questions

- OQ-100 (§8 / §9 Gate 1 mechanics) The pipeline registry now carries `GATES = {bid_no_bid: gate1}` and `plan_steps(step, gates_cleared=...)` ends the plan after a gated step, for a single-step request as well as for `all`. A gate is cleared by the pursuit's own state rather than by a run parameter: `services/pursuits.cleared_gates(pursuit)` returns `("gate1",)` once `pursuits.decision == 'bid'`, and `jobs/run_agents` reads the pursuit before planning, so re-dispatching the SAME run id after the decision simply plans past the gate and skips the steps already done. A `no_bid` clears nothing and resumes nothing. M5-10 adds `GATE_2` after `red_team` the same way.
- OQ-101 (§8 agent 4 scorecard vs `bid_no_bid_weights`) SPEC's scorecard names the fifth criterion "value" while the design calls the field `value_fit`; the Scorecard schema keeps `value_fit` (clearer next to `win_probability`) and `Scorecard.scores()` maps it onto the preferences key `value`, so the profile's weights validate unchanged. The model's own `recommendation` is stored verbatim next to the weighted total and `suggested_recommendation` (bid >= 65, watch >= 45, else no_bid); a disagreement is shown rather than resolved, because the weights are the tenant's policy and the reasons are the model's. A profile whose stored weights no longer validate falls back to the defaults with a warning instead of failing the run.
- OQ-102 (§10.3 PATCH /pursuits/{id} before M6-01) The acceptance line "stage cannot move to Drafting without a bid decision" needs a stage route, so this pass adds a deliberately small `PATCH /api/v1/pursuits/{id}` (stage, owner_user_id; bid manager / owner) whose only rule is `services/pursuits.check_stage_transition`: an unknown stage is 422, `drafting` without `decision == 'bid'` is 409. M6-01 extends that one helper with the full board rules (ordering, key dates, drag-and-drop) instead of adding a second rule set in the route.

- OQ-105 (§8 agent 8 "drafts auto-revised once") "Once" is enforced per SECTION, not per run: the revision writes `flags.red_team.revised = true` on the new version, and a later red-team run sees `already_revised` and turns that section's findings into comments instead of rewriting it again. A human edit (author user) clears the marker, so a section a person reworked is eligible for one more agent revision on the next review. The run always writes a NEW `red_team` artifact version, so the history shows both reviews.
- OQ-106 (§8 which findings really got fixed) The report cannot be re-run cheaply, so `core.red_team.remaining_issues` decides deterministically where it can and trusts the revision only where it must: a `page_limit` is resolved when the re-measured body fits, an `unsupported_claim` when its verbatim sentence is gone from the new body (or, with no sentence, when the grounding validator reports 0 unsupported claims), and `non_compliant` / `missing_requirement` / `clarity` only when the revision listed the finding in `addressed`. Everything else becomes a review comment, so a revision that claims a fix it did not make still leaves the finding visible.
- OQ-107 (§8 "page-limit overruns") Page counts are computed, never modelled: `core.page_estimate` divides the word count by the words one page holds under the solicitation's own font size and margins (500 words at 12 pt with 1 inch margins, scaled by 1/size^2 and by the text area, clamped to 120-1500). The prompt explicitly tells the reviewer NOT to judge length and every `page_limit` issue the model returns is dropped and replaced. A whole-package overrun against `format_rules.page_limit` is attached to the LONGEST section, because that is the one a reviewer cuts first.
- OQ-108 (§8 Gate 2 vs "mark final") Gate 2 is `POST /pursuits/{id}/approve-package` (bid manager / tenant owner): it records `pursuits.package_approved_by/at`, marks every section approved, moves the stage to `final_approval`, audits `pursuit.package_approved` and resumes the paused run. It deliberately does NOT make the export final -- SPEC 11's "internal footer until a human marks it final" is a second, separate step (`package_final`, M5-13), so approving the content and releasing the document are two decisions.

- OQ-109 (§8 "human-in-the-loop edits are diffed") The diff is taken over `body_text`, not `body_html`, and `core.diffs.split_for_diff` collapses runs of whitespace and splits paragraphs over 200 characters into sentences before diffing: a TipTap editor re-wraps markup on every keystroke, so an HTML diff would record reflow as feedback and a paragraph-level diff would only ever say "the paragraph changed". A save whose rendered text is unchanged writes no `draft_feedback` row at all.
- OQ-110 (§8 what "feedback" a future prompt may see) `services/draft_feedback.recent_examples(session, tenant_id, section_kind, k)` keys on the outline SECTION ID (technical-approach, past-performance ...), which is stable across pursuits, and returns only rows whose `from_author` is `agent` -- a writer editing another writer's wording is not a lesson about how the agent should have drafted it. It filters on `tenant_id` on top of the session's RLS, so the query is wrong twice before it could ever read another tenant's proposal text; an integration test asks for tenant B's id from tenant A's session and gets nothing.
